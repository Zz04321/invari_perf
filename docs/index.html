SWE-Perf Task

SWE-Perf 到底给 agent 什么任务

SWE-Perf 可以理解成“性能版 SWE-bench”：它给 agent 一个真实仓库、 一段性能优化任务描述、若干目标函数和官方评估脚本。Agent 要输出 patch，最后由 SWE-Perf 判断：

  1. 补丁能不能 apply。
  2. 正确性测试能不能通过。
  3. 性能测试有没有变快。

字段

任务信息

repo
要修改的真实仓库
instance_id
任务编号
problem
性能优化任务描述
targets
可能相关的函数

流程

SWE-Perf 怎么评分

  1. 给 agent 一个真实仓库任务。
  2. agent 生成代码修改。
  3. SWE-Perf 应用修改并运行测试。
  4. 比较正确性和性能结果。

输出

agent 要交代码修改

这里的 patch 就是一组代码改动。SWE-Perf 不只看它写得像不像， 而是会真的应用到仓库里跑测试。

工具本身

Daikon 做什么

  1. 运行程序，收集变量值。
  2. 观察函数入口和出口。
  3. 总结多次运行中经常成立的关系。
  4. 输出候选的运行时规律。

输入

Daikon 需要什么

Daikon 不是只看源码。它需要程序真实运行时的值： 函数参数、返回值、对象状态，以及这些值出现了多少次。

输出形态

输出是候选关系

例如“输入是整数时，返回值等于输入”。它不是补丁， 也不是完整证明，而是后续分析可以使用的证据。

Case Study

把两个模块放到一个真实例子里

SWE-Perf 实例

astropy__astropy-16058

这是一个真实 Astropy 性能优化任务。SWE-Perf 给出仓库、目标函数和性能测试。

目标函数

validate_power

性能测试运行时会反复调用它。如果它每次都多做一点工作， 整体耗时就会被放大。

问题模式

检查 + 转换混在一起

很多时候只需要检查输入是否合法，但原实现还会顺手做转换。

这个 case 的问题

validate_power(p):
    1. 检查 p 是否合法
    2. 把 p 转成更标准的表示
    3. 返回处理后的 p

这里的性能浪费是：很多时候只需要“检查是否合法”，却一起做了 “转换成标准表示”的额外工作。

也就是说，这不是“输出错了”的正确性 bug。它更像 “行为没错，但把两个职责混在一起，导致热路径做了不必要工作”。

      Baseline Codex

      只给官方 SWE-Perf 任务提示，不加 Daikon 证据。

      • 补丁应用 / 测试运行 / 任务成功：yes
      • Mean duration: 0.01084s -> 0.01001s
      • Relative improvement: 7.67%

      Codex + Daikon skill

      同一个任务，但提示里加入 Daikon skill 生成的运行时语义证据。

      • 补丁应用 / 测试运行 / 任务成功：yes
      • Mean duration: 0.00820s -> 0.00741s
      • Relative improvement: 9.61%
      另一个观察： 性能优化不只会改变耗时，也可能改变程序运行时表现出来的规律。 我们先看了 20 个真实 SWE-Perf 任务，其中 12 个任务 可以成功跑完 Daikon 的修改前/修改后对比；在这 12 个里面， 有 3 个任务的 Daikon 结果发生了变化。 这不表示这些优化是错的，而是说明这种变化需要进一步解释： 例如 astropy__astropy-16058 有变化，因为它把 validate_power 拆成了“只检查”和“规范化”两个职责； astropy__astropy-13496 没有变化，因为它只是安全地加了缓存， 并且没有把缓存写进序列化状态。

      Codex + Daikon skill 的补丁形态

      它不是简单删除逻辑，而是把一个混合职责函数拆成“快路径”和“慢路径”。 

      def validate_power(p):
    # 快路径：只做轻量检查
    if p.__class__ is int or p.__class__ is Fraction:
        return p
    ...
    return p

def sanitize_power(p):
    # 慢路径：需要规范化表示时再做
    p = maybe_simple_fraction(p)
    ...

      然后只在真正需要“规范化幂次表示”的地方调用 sanitize_power。

      这正好对应性能浪费的结构：常见输入走更便宜的分支； 不确定的输入继续走完整处理逻辑。
